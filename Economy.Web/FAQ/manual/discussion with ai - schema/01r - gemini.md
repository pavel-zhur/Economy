Хорошо, давай разберем твои вьюшки и подумаем над сущностями для БД. Цель — простые, но гибкие сущности. Я постараюсь избегать очевидного и сконцентрируюсь на ключевых моментах и возможных вариантах.

## Основные сущности (Core Entities)

Вот мой взгляд на основные сущности, которые могут лечь в основу твоего приложения:

---

### 1. `User` (Пользователь) 👤
* **Смысл:** Стандартная сущность для идентификации пользователя.
* **Поля:** `id`, `username`, `email`, `password_hash`, `created_at`.
* *Это очевидно, так что не будем углубляться.*

---

### 2. `Account` (Счет / Кошелек) 💳
* **Смысл:** Представляет реальный источник или хранилище денег пользователя (банковский счет, наличные, кредитная карта). Это "физическое" местонахождение денег до их концептуального распределения по планам.
* **Поля:**
    * `id`
    * `user_id` (связь с пользователем)
    * `name` (например, "Карта Сбера", "Наличные")
    * `type` (например, 'bank_account', 'cash', 'credit_card', 'e_wallet')
    * `currency_code` (например, 'RUB', 'USD')
    * `balance` (текущий фактический баланс, обновляемый через `InventoryEntry` или вручную)
    * `is_archived` (флаг для скрытия неактуальных счетов)
* **Связи:**
    * Один `User` может иметь много `Account`.
    * `Transaction` происходит по конкретному `Account`.
* **Поведение:** Баланс этого счета сверяется с помощью `InventoryEntry`. Это источник "земной правды" о количестве денег.

---

### 3. `Plan` (План / Конверт / Цель) 🎯
* **Смысл:** Это **ключевая и очень гибкая сущность**. Представляет собой концептуальный "контейнер" для денег, который может быть:
    * Запланированным расходом (разовым или регулярным).
    * Накопительной целью (фонд, копилка).
    * Категорией бюджета (например, "Продукты", "Транспорт").
    * Хранилищем (просто место для денег без конкретной цели, но выделенное).
    * Планируемым доходом (как категория, куда будут поступать деньги).
* **Поля:**
    * `id`
    * `user_id`
    * `name` (например, "Отпуск 2026", "Квартплата", "Фонд ЧП", "Продукты")
    * `type` (очень важное поле для логики: 'expense_planned', 'savings_goal', 'fund', 'budget_category', 'storage', 'income_category')
    * `parent_plan_id` (опционально, для иерархии, например, "Крупные покупки" -> "Новый телефон")
    * `target_amount` (целевая сумма, для 'savings_goal', 'expense_planned')
    * `target_date` (целевая дата, для 'savings_goal', 'expense_planned')
    * `current_allocated_amount` (сколько *фактически* денег сейчас выделено на этот план; рассчитывается или хранится)
    * `is_auto_spend_all` (флаг для планов, которые должны тратить все поступления, например, ежемесячный бюджет на продукты)
    * `pessimistic_target_amount` (для Вьюхи 3)
    * `status` ('active', 'achieved', 'archived', 'cancelled')
    * `created_at`, `updated_at`
* **Связи:**
    * `User` -> `Plan` (один ко многим)
    * `Plan` -> `Plan` (через `parent_plan_id` для иерархии)
    * `PlanEvent` (см. ниже) будут связаны с `Plan`.
* **Поведение:**
    * Его "баланс" ( `current_allocated_amount`) формируется из `Allocations` (см. ниже).
    * Позволяет группировать и управлять финансами на более высоком уровне, чем просто транзакции.
    * Тип 'expense_planned' важен для Вьюхи 1.
    * Типы 'savings_goal', 'fund' важны для Вьюх 2, 3, 9.

---

### 4. `Transaction` (Транзакция) 💸
* **Смысл:** Запись о фактическом движении средств (доход или расход). Это основа для всех фактических данных.
* **Поля:**
    * `id`
    * `user_id`
    * `account_id` (с какого/на какой `Account` пришли/ушли деньги)
    * `description` (комментарий)
    * `amount` (сумма; положительная для дохода, отрицательная для расхода)
    * `currency_code`
    * `transaction_date` (когда фактически произошла транзакция)
    * `category_id` (опционально, ссылка на `Category` для дополнительной классификации)
    * `linked_plan_event_id` (опционально, если эта транзакция закрывает запланированное событие)
    * `created_at` (когда запись добавлена в систему)
* **Связи:**
    * `User` -> `Transaction`
    * `Account` -> `Transaction`
    * `Category` -> `Transaction` (опционально)
    * `PlanEvent` -> `Transaction` (опционально)
* **Поведение:**
    * Неизменяемы после создания (или должна быть история изменений).
    * Используются для расчета фактических балансов `Account` (Вьюха 5) и анализа реальных трат/поступлений.

---

### 5. `PlanEvent` (Событие Плана / Планируемая Операция) 🗓️
* **Смысл:** Запись о *будущем* или *повторяющемся* ожидаемом движении средств, связанном с определенным `Plan` или без привязки к конкретному плану (например, ожидаемая зарплата). Это может быть планируемый доход или расход.
* **Поля:**
    * `id`
    * `user_id`
    * `plan_id` (опционально, если событие относится к конкретному плану, например, "платеж по кредиту" для плана "Кредит")
    * `description`
    * `amount` (сумма; положительная для дохода, отрицательная для расхода)
    * `currency_code`
    * `event_date` (ожидаемая дата события)
    * `is_recurring` (булево)
    * `recurrence_rule` (например, RRULE строка или JSON для описания правила повторения: "ежемесячно 5 числа")
    * `type` ('income', 'expense')
    * `status` ('pending', 'fulfilled', 'skipped', 'cancelled')
    * `end_date` (для повторяющихся событий)
* **Связи:**
    * `User` -> `PlanEvent`
    * `Plan` -> `PlanEvent` (опционально)
    * Одна `Transaction` может "закрывать" один `PlanEvent`.
* **Поведение:**
    * Основа для Вьюхи 1 (Планируемые расходы).
    * Движущая сила для всех прогнозов (Вьюхи 3, 4, 8, 10, 12, 17, 18).
    * При наступлении `event_date` система может предлагать создать фактическую `Transaction` или автоматически создавать ее (если настроено).

---

### 6. `Allocation` (Распределение / Связка) 🔗
* **Смысл:** Это **критически важная "соединительная" сущность**, которая показывает, как деньги *концептуально* перемещаются между счетами (`Account`), планами (`Plan`), и как транзакции (`Transaction`) связаны с планами. Это может быть как фактическое распределение, так и правило для будущего.
* **Поля:**
    * `id`
    * `user_id`
    * `source_account_id` (опционально, если деньги идут с реального счета)
    * `source_plan_id` (опционально, если деньги идут из другого плана - трансфер)
    * `destination_plan_id` (в какой план направляются деньги)
    * `transaction_id` (опционально, какая фактическая транзакция вызвала это распределение или покрывается им)
    * `plan_event_id` (опционально, какое планируемое событие связано с этим распределением)
    * `amount` (сумма распределения)
    * `allocation_date` (когда произошло распределение)
    * `type` ('funding_plan', 'expense_from_plan', 'transfer_between_plans', 'income_to_plan_rule')
    * `is_rule_based` (булево, если это правило для будущих распределений, а не свершившийся факт)
* **Связи:** Соединяет `Account`, `Plan`, `Transaction`, `PlanEvent`.
* **Поведение:**
    * **Ключ к Вьюхе 2 ("Распределение фактических денег по планам"):** Сумма `Allocation.amount` где `destination_plan_id` = ID плана и тип `funding_plan` или `transfer_between_plans` (приход) минус расходы.
    * **Ключ к Вьюхе 4 ("Распределение доходов по планам"):**
        * Для прошлых доходов: доходная `Transaction` может иметь несколько `Allocation`, направляющих части дохода в разные `Plan`.
        * Для будущих доходов: `PlanEvent` (доход) может иметь связанные `Allocation` с `is_rule_based = true`, определяющие, как он *будет* распределен.
    * Позволяет отслеживать, что "на плане X лежат деньги, пришедшие от зарплаты Y" или "расход Z был покрыт из плана W".
    * Обеспечивает условие "Отображаются только те планы расходов, на которые есть фактические средства" (Вьюха 1). У плана расходов должны быть `Allocation` типа 'funding_plan'.

---

### 7. `Category` (Категория транзакций) 🏷️
* **Смысл:** Пользовательские категории для тегирования `Transaction` (например, "Продукты", "Транспорт", "Зарплата"). Используется для анализа и отчетов, отличается от `Plan.type`.
* **Поля:** `id`, `user_id`, `name`, `type` ('income', 'expense'), `parent_category_id` (для иерархии).
* **Связи:** `Transaction` может иметь `category_id`.
* **Поведение:** Используется в Вьюхе 4 для группировки расходов.

---

### 8. `InventoryEntry` (Запись инвентаризации / Сверка баланса) 📊
* **Смысл:** Фиксирует фактический баланс `Account` на определенную дату, введенный пользователем.
* **Поля:** `id`, `user_id`, `account_id`, `entry_date`, `reported_balance`.
* **Связи:** Принадлежит `Account`.
* **Поведение:** Используется в Вьюхе 5 для сравнения с расчетным балансом по `Transaction`.

---

### 9. `ForecastLog` (Лог прогнозов) (для Вьюхи 3, 10, 11, 16, 17, 18) 📈
* **Смысл:** Сохраняет состояния прогнозов и сценариев. Это может быть сложнее, чем просто одна таблица, но для начала:
* **Поля:**
    * `id`
    * `user_id`
    * `log_date` (когда был сделан/сохранен этот прогноз/сценарий)
    * `name` (например, "Базовый прогноз Июнь", "Сценарий: покупка машины")
    * `type` ('baseline_forecast', 'what_if_scenario', 'historical_deviation_snapshot')
    * `data` (JSON или XML, хранящий параметры сценария или детали прогноза на тот момент: какие `PlanEvent` учитывались, какие изменения были внесены в "Что если")
    * `reference_date_from` (начальная дата прогноза)
    * `reference_date_to` (конечная дата прогноза)
* **Связи:** Может быть связан с `Plan` (например, прогноз для конкретного плана).
* **Поведение:**
    * **Вьюха 3:** Позволяет сравнивать текущий прогноз с прошлыми (`log_date`).
    * **Вьюха 10, 18 ("Что если"):** Сохраняет параметры введенных изменений.
    * **Вьюха 11 ("История отклонений"):** Может хранить "замороженные" плановые значения на начало периода для сравнения с фактическими.
    * Для полноценного "что-если" и детализированных прогнозов может понадобиться отдельная сущность `ScenarioParameter` (`forecast_log_id`, `changed_entity_type`, `changed_entity_id`, `parameter_name`, `old_value`, `new_value`).

---

## Тонкие моменты и упрощения:

* **"Планируемые расходы... на которые есть фактические средства" (Вьюха 1):**
    Решается через `Allocation`. У `Plan` типа 'expense_planned' должен быть положительный `current_allocated_amount`, сформированный через `Allocation` из реальных денег или других планов. Отображаем `PlanEvent` (расходные), связанные с такими "профинансированными" планами.

* **"Распределение фактических денег по планам" (Вьюха 2):**
    Это `Plan.current_allocated_amount`. Этот баланс изменяется записями в `Allocation`.

* **"Будущее распределение по фондам и накоплениям" (Вьюха 3) и "Баланс планов во времени" (Вьюха 8):**
    Рассчитывается на основе текущего `Plan.current_allocated_amount` + все будущие `PlanEvent` (доходы и расходы), связанные с этим планом или общие доходы/расходы, распределяемые согласно правилам в `Allocation` (`is_rule_based = true`). `ForecastLog` помогает сохранить и сравнить эти проекции.

* **"Время задержки средств" (Вьюха 6):**
    Самый сложный момент для точного отслеживания "конкретного рубля".
    * **Вариант 1 (Приближенный, по плану):** Если расход (`Transaction`) связан с `Plan` через `Allocation` (типа `expense_from_plan`), а сам `Plan` ранее пополнялся (`Allocation` типа `funding_plan`), можно взять разницу дат между расходной транзакцией и датой последнего значимого пополнения этого плана.
    * **Вариант 2 (Упрощенный, по среднему):** Рассчитывать среднее время между датой поступления *любого* дохода на `Account` и датой *любого* расхода с этого `Account`. Менее точно, но проще.
    * **Вариант 3 (Без прямого связывания денег):** Можно анализировать не "конкретные деньги", а время, которое *эквивалентная сумма* находится на счетах или в планах. Например, если пришел доход 10000, а через 5 дней расход 2000, то можно считать, что 2000 "пролежали" 5 дней. Это требует логики FIFO/LIFO на уровне счетов/планов.
    Сущность `Allocation` с `transaction_id` и `plan_event_id` может помочь, если пытаться проследить цепочку, но это будет сложно и не всегда однозначно. Я бы начал с упрощенного подхода или анализа на уровне планов.

* **"Неподкрепленные транзакции" (Вьюха 7):**
    * Расходные `Transaction`, у которых нет соответствующей `Allocation` типа `expense_from_plan`.
    * Доходные `Transaction`, сумма которых больше, чем сумма `Allocation` типа `funding_plan`, исходящих от этой транзакции.

* **"Эталонное распределение доходов" (Вьюха 4):**
    Можно реализовать через специальные `Plan` с типом 'reference_distribution_target' и процентным соотношением. Или как набор правил в отдельной таблице `ReferenceDistributionRule` (`user_id`, `plan_id_target`, `percentage`).

* **Простота управления:**
    * **`Plan` как центр всего:** Многие операции (бюджетирование, цели, планируемые траты) крутятся вокруг `Plan`.
    * **`Allocation` для гибкости:** Эта сущность, хоть и добавляет связей, но именно она дает гибкость в распределении средств, не создавая при этом десятков мелких таблиц для каждого типа связи.
    * **`PlanEvent` для будущего:** Четкое разделение фактических `Transaction` и планируемых `PlanEvent`.
    * Использование `type` полей для изменения логики вместо создания множества похожих таблиц.

## Возможные альтернативы и дополнения:

* **`Tag` (Тег):** Более гибкая система меток, чем `Category`. Транзакция или План могут иметь много тегов. Полезно для произвольного анализа.
* **`BudgetPeriod` (Бюджетный период):** Если есть четкие бюджетные циклы (например, месяц), можно ввести сущность для хранения общих сумм бюджета на период и отслеживания прогресса по нему. Но это можно реализовать и через `Plan` с типом `budget_category` и повторяющиеся `PlanEvent`.

Эта модель стремится к тому, чтобы основные сущности были относительно простыми, но их комбинация и связи (особенно через `Allocation`) позволяли реализовать сложный функционал. Ключ в том, чтобы `Allocation` была достаточно умной для обработки разных сценариев (фактическое распределение, правила, трансферы).
