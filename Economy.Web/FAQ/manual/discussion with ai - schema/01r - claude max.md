
Анализируя описанные представления, я вижу несколько интересных архитектурных решений. Позвольте предложить варианты дизайна сущностей:

## Основные тонкие моменты в требованиях:

1. **Многоуровневая природа планов** - есть фонды, хранилища, запланированные расходы, и они могут иметь иерархию
2. **Временная динамика** - одни и те же сущности должны показывать прошлое, настоящее и прогнозы
3. **Распределение vs фактическое использование** - деньги могут быть распределены по одному плану, а потрачены на другой
4. **Двойная бухгалтерия планов** - баланс по транзакциям vs баланс по инвентаризации

## Вариант 1: План-центричная архитектура

### Основные сущности:

**Plan** - универсальная сущность для всех видов планирования:
- `type`: enum (FUND, STORAGE, PLANNED_EXPENSE, PLANNED_INCOME, GOAL)  
- `parent_plan_id`: ссылка на родительский план (для иерархии)
- `auto_spend_all`: boolean (автоматическое израсходование)
- `target_amount`, `target_date`: для целей накоплений
- `recurrence_rule`: правила повторения для регулярных планов

**Transaction** - все денежные операции:
- `amount`, `date`, `wallet_id`, `category_id`
- `source_plan_id`: из какого плана тратим (может быть null для неподкрепленных)
- `target_plan_id`: в какой план направляем (может быть null)

**PlanBalance** - снимки балансов планов во времени:
- `plan_id`, `date`, `balance`
- Позволяет отслеживать динамику и строить графики

**DistributionRule** - правила автораспределения доходов:
- `source_criteria`: условия (категория дохода, сумма, etc.)
- `target_plan_id`, `percentage` или `fixed_amount`

### Особенности этого подхода:
- План может быть и фондом и целью одновременно
- Иерархия планов решается через parent_plan_id
- Прогнозы строятся из планов типа PLANNED_*

## Вариант 2: Разделение ответственности

### Основные сущности:

**Fund** - накопительные фонды:
- `name`, `auto_spend_all`, `parent_fund_id`

**Goal** - конкретные цели накоплений:
- `fund_id`, `target_amount`, `target_date`, `priority`

**PlannedOperation** - запланированные доходы/расходы:
- `type`: INCOME/EXPENSE
- `amount`, `planned_date`, `recurrence_rule`
- `fund_id`: связь с фондом (откуда тратим/куда направляем)

**Transaction** - как в первом варианте, но:
- `fund_id`: связь с фондом
- `planned_operation_id`: если выполняем запланированную операцию

### Особенности:
- Более четкое разделение концепций
- Цели отделены от фондов
- Легче валидировать бизнес-правила

## Вариант 3: Event-driven архитектура

**MoneyEvent** - все денежные события:
- `type`: INCOME, EXPENSE, TRANSFER, ALLOCATION, GOAL_SET
- `amount`, `date`, `source_account`, `target_account`
- `metadata`: JSON с дополнительными данными

**Account** - обобщенные счета:
- `type`: WALLET, FUND, GOAL, PLANNED_OPERATION
- `name`, `parent_account_id`

**Snapshot** - периодические снимки состояний:
- `account_id`, `date`, `balance`, `metadata`

### Особенности:
- Все состояния вычисляются из событий
- Максимальная гибкость для новых требований
- Хорошо подходит для "что если" сценариев

## Рекомендация: Вариант 1.5 (гибрид)

Предлагаю комбинированный подход:

**Plan** - основная сущность со строгой типизацией:
```python
class PlanType(Enum):
    FUND = "fund"              # Накопительный фонд
    GOAL = "goal"              # Цель с датой
    PLANNED_EXPENSE = "planned_expense"  
    PLANNED_INCOME = "planned_income"
    STORAGE = "storage"        # Временное хранилище
```

**PlanConfig** - конфигурация плана (JSON):
- Для GOAL: `{"target_amount": 100000, "target_date": "2024-12-31"}`
- Для FUND: `{"auto_spend_all": false, "distribution_rules": [...]}`
- Для PLANNED_*: `{"recurrence": "monthly", "day": 15}`

**BalanceSnapshot** - регулярные снимки:
- Решает проблему пересчета балансов во времени
- Позволяет строить графики без тяжелых вычислений

**WhatIfScenario** - отдельная сущность для моделирования:
- `base_date`, `changes`: JSON с изменениями
- `results`: кешированные результаты расчетов

### Ключевые преимущества:
1. **Простота**: один тип "план" для всего
2. **Гибкость**: JSON-конфиг позволяет добавлять новые поля без миграций
3. **Производительность**: снимки балансов для быстрых запросов
4. **Расширяемость**: легко добавить новые типы планов

Этот подход позволит реализовать все описанные представления, сохранив простоту в управлении и возможность эволюции системы.
