# Архитектурное решение: Разделение на два универсальных сервиса

## Суть решения

Вместо попыток создать единую архитектуру, которая решает все проблемы сразу, разделяем систему на два независимых универсальных сервиса, каждый из которых оптимизирован для своего класса задач.

## Сервис 1: Stream Interpreter

### Назначение
Универсальный интерпретатор потоковых сообщений от пользователей в структурированные данные.

### Характеристики
- **Источники**: Telegram, голосовые сообщения, текст, изображения
- **Принцип работы**: AI интерпретирует сообщения в схему без глубокого диалога
- **Event Sourcing**: Да, источником истины являются исходные сообщения пользователя
- **Миграции**: На уровне сообщений с AI-powered реинтерпретацией
- **Универсальность**: Полностью domain-agnostic, работает с любыми типами данных

### Типичные use cases
- Учет расходов: "купил хлеб за 50 рублей"
- Инвентаризации: "на счету Сбера 15000"
- Фиксация событий: "встретился с Петей"
- Логирование активности: "2 часа работал над проектом"

### Архитектурные особенности
- Исходные сообщения неизменяемы и хранятся навсегда
- AI может реинтерпретировать всю историю при смене схемы
- Schema + Cookbook определяют интерпретацию
- Preview mode для проверки миграций
- Feedback loop для улучшения интерпретации

## Сервис 2: Schema-Driven Data Platform

### Назначение
Универсальная система планирования и анализа с гибкой схемой данных.

### Характеристики
- **Интерфейс**: Веб-UI с формами, дашбордами, отчетами
- **Принцип работы**: Классическая схема-специфичная работа с данными
- **Event Sourcing**: Нет, только текущее состояние (+ бизнес-история где нужно)
- **Хранение**: YAML файлы в Git репозитории
- **Миграции**: Данные в данные с AI-powered превью
- **Универсальность**: Полностью configurable, работает с любыми схемами

### Типичные use cases
- Финансовое планирование: планы, цели, прогнозы
- Проектное планирование: задачи, ресурсы, timeline
- Инвентарное планирование: закупки, остатки, прогнозы
- Любое структурированное планирование

### Архитектурные особенности
- Данные в YAML для читаемости и diff-friendly изменений
- Схема хранится в том же Git репозитории
- AI-powered миграции с preview и rollback
- Public Git с примерами схем и конфигураций
- Private Git для пользовательских данных

## Взаимодействие сервисов

### Принцип интеграции
Schema-Driven Data Platform подключается к Stream Interpreter через API для получения интерпретированных данных.

### Схема взаимодействия
```
Telegram → Stream Interpreter (AI интерпретация) → Structured Data → API → Schema-Driven Data Platform
```

### Гибкость подключения
- Schema-Driven Data Platform не хранит данные из Stream Interpreter
- При миграции схемы Stream Interpreter просто перенастраиваются API маппинги
- Можно подключать множественные источники данных
- Можно использовать Schema-Driven Data Platform без Stream Interpreter

## Преимущества решения

### 1. Архитектурная ортогональность
- Каждый сервис решает свой класс проблем оптимальным образом
- Нет компромиссов и архитектурных конфликтов
- Event sourcing там где нужен, гибкая схема там где нужна

### 2. Независимая эволюция
- Схемы и миграции каждого сервиса развиваются независимо
- Проблемы одного сервиса не влияют на другой
- Можно тестировать и улучшать каждый сервис отдельно

### 3. Универсальность
- Оба сервиса domain-agnostic
- Можно использовать для финансов, проектов, инвентаря, CRM, etc.
- Потенциал для open-source и коммерциализации

### 4. Простота понимания
- Каждый сервис имеет четкую ответственность
- Легче объяснить, документировать, поддерживать
- Меньше когнитивной нагрузки при разработке

### 5. Гибкость развертывания
- Можно использовать только один из сервисов
- Можно интегрировать с существующими системами
- Масштабируются независимо

## Недостатки и риски

### 1. Сложность интеграции
- Два отдельных сервиса означают больше moving parts
- Нужно поддерживать совместимость API между сервисами
- Более сложное развертывание и мониторинг

### 2. Дублирование схем
- Схемы данных могут дублироваться между сервисами
- Нужна синхронизация изменений схем
- Риск рассинхронизации при миграциях

### 3. Задержка данных
- Данные идут через цепочку Telegram → Stream → API → Schema-Driven Data Platform
- Возможные задержки в real-time обновлениях
- Нужна обработка сетевых сбоев и таймаутов

### 4. Версионирование API
- При изменении схемы Stream Interpreter нужно обновлять API
- Backward compatibility может стать проблемой
- Нужна стратегия версионирования интерфейсов

## Рекомендации по развитию

### Фаза 1: MVP Stream Interpreter
- Базовый Telegram bot
- Простая схема интерпретации
- AI интерпретация через OpenAI API
- Файловое хранение

### Фаза 2: MVP Schema-Driven Data Platform  
- YAML-based планировщик
- Git integration
- Простой Web UI
- API для внешних данных

### Фаза 3: Integration
- API между сервисами
- Схема синхронизации
- End-to-end workflow

### Фаза 4: Advanced Features
- Advanced AI migrations
- Schema registry
- Multi-tenant support
- Public schema marketplace

## Заключение

Разделение на два универсальных сервиса представляется оптимальным решением, которое:

1. **Решает архитектурные конфликты** между event sourcing и гибкими схемами
2. **Обеспечивает универсальность** - каждый сервис применим к широкому спектру задач
3. **Упрощает разработку** - четкое разделение ответственности
4. **Предоставляет гибкость** - можно использовать сервисы независимо

Основные риски связаны с интеграцией и синхронизацией, но они управляемы через правильную архитектуру API и схем.

Рекомендуется начать с MVP каждого сервиса по отдельности, затем интегрировать их через простое API, постепенно развивая более сложные возможности.
