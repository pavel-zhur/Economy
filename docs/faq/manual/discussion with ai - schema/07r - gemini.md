
Отлично, давайте последовательно проверим каждую из 18-ти вьюх на предмет реализуемости с использованием предложенной модели данных. Я буду краток.

**Сущности для справки:** `User`, `Account`, `InventoryEntry`, `Transaction`, `Category`, `Plan`, `ForecastEntry`, `DistributionRule`, `Scenario`, `TransactionPlanLink`. Ключевые расчетные поля: `Plan.CurrentActualAllocatedAmount`, `Plan.ProjectedBalance(date, scenario_tag)`, `Plan.CalculatedDiscrepancy`.

---

1.  **Планируемые расходы (прошлые и будущие)**
    *   **Данные:** `ForecastEntry` (тип `expense`, `event_date`, `linked_plan_id`, `amount_by_scenario`), `Plan` (`CurrentActualAllocatedAmount`).
    *   **Реализуемость:** Да. Отбираем `ForecastEntry` (расходы), проверяем `Plan.CurrentActualAllocatedAmount` связанного плана. Сортируем.
    *   **Управление:** Пользователь создает/редактирует `ForecastEntry` и планы.

2.  **Распределение фактических денег по планам**
    *   **Данные:** `Plan` (`CurrentActualAllocatedAmount`, `type`, возможно, новый флаг `is_transitory` или `type='transitory'`), `Account` (для общего баланса).
    *   **Реализуемость:** Да. Отображаем `CurrentActualAllocatedAmount` для активных не-транзитных планов в % от общей суммы на `Account`.
    *   **Управление:** Пользователь классифицирует планы по типам.
    *   **Предложение:** Добавить `Plan.type = 'transitory'` или флаг `Plan.is_auto_spend_all` для явного исключения.

3.  **Будущее распределение по фондам и накоплениям**
    *   **Данные:** `Plan` (type `fund`, `goal`, `target_amount`, `target_date`), `Scenario` (для `pessimistic`), `ForecastEntry`, `DistributionRule`.
    *   **Реализуемость:** Да. `ProjectedBalance(date, scenario_tag)` для графиков. `CurrentActualAllocatedAmount` для факта. `target_amount/date` для точек цели.
    *   **Сравнение с прошлыми прогнозами:** Требует механизма снимков прогнозов (например, сущность `ForecastSnapshot` или пользователь вручную клонирует/именует `Scenario`). Без этого сравнение ограничено текущими сценариями.
    *   **Предложение (для истории прогнозов):** Рассмотреть `ForecastSnapshot(snapshot_id, date_created, scenario_tag, plan_id, forecasted_balances_json)`.

4.  **Распределение доходов по планам, расходам и категориям (прошлое и будущее)**
    *   **Данные:** `Transaction` (`type`, `category_id`), `TransactionPlanLink`, `ForecastEntry` (`type='income'`), `DistributionRule`, `Plan`, `Category`.
    *   **Реализуемость:** Да. Прошлое – по `Transaction` и `TransactionPlanLink`. Будущее – по `ForecastEntry` (`income`) и `DistributionRule`. Категории – из `Transaction`. "Эталонное распределение" – через специальный `Scenario`.
    *   **Управление:** Пользователь создает правила, связывает транзакции, категоризирует.

5.  **Инвентаризация и соответствие баланса кошельков**
    *   **Данные:** `Account`, `InventoryEntry`, `Transaction`.
    *   **Реализуемость:** Да. График из `InventoryEntry.reported_balance` и накопленной суммы `Transaction`.
    *   **Управление:** Пользователь проводит инвентаризации.

6.  **Время задержки средств**
    *   **Данные:** `Transaction`.
    *   **Реализуемость:** Сложно для "каждого рубля". Модель напрямую не поддерживает.
    *   **Предложение:** Реализовать упрощенно: среднее время нахождения средств на планах типа `fund` (между пополнением и списанием с этого плана). Либо отказаться от этой вьюхи в пользу простоты модели.

7.  **Планы с отрицательным балансом и неподкрепленные транзакции**
    *   **Данные:** `Plan` (`CurrentActualAllocatedAmount`, `parent_plan_id`), `Transaction`, `TransactionPlanLink`.
    *   **Реализуемость:** Да. Фильтруем планы по `CurrentActualAllocatedAmount < 0` и отсутствию родителя. Транзакции – по отсутствию связей в `TransactionPlanLink`.
    *   **Управление:** Пользователь видит проблемы и корректирует.

8.  **Баланс планов во времени**
    *   **Данные:** `Plan` (`CurrentActualAllocatedAmount`, `ProjectedBalance`).
    *   **Реализуемость:** Да. График из истории `CurrentActualAllocatedAmount` и будущего `ProjectedBalance`.
    *   **Управление:** Пользователь анализирует и корректирует планы/прогнозы.

9.  **Цели накоплений и прогресс**
    *   **Данные:** `Plan` (type `goal`, `target_amount`, `target_date`, `CurrentActualAllocatedAmount`, `ProjectedBalance`).
    *   **Реализуемость:** Да. Все данные для расчета прогресса, остатка времени и темпа есть.
    *   **Управление:** Пользователь ставит цели в планах.

10. **Моделирование "Что если"**
    *   **Данные:** `Scenario`, `ForecastEntry`, `DistributionRule`, `Plan`.
    *   **Реализуемость:** Да. Пользователь создает новый `Scenario` и изменяет в нем `ForecastEntry`/`DistributionRule`. Система пересчитывает прогнозы.
    *   **Управление:** Пользователь управляет сценариями.

11. **История отклонений от плана**
    *   **Данные:** `Plan` (`CalculatedDiscrepancy`), `ForecastEntry`, `TransactionPlanLink`.
    *   **Реализуемость:** Да. Сравниваем плановые суммы из `ForecastEntry` (для `baseline` сценария) с фактическими из связанных `Transaction` за период. `CalculatedDiscrepancy` это агрегирует на уровне плана.
    *   **Управление:** Пользователь анализирует.

12. **Анализ остатка средств до следующего дохода**
    *   **Данные:** `Account` (текущий общий баланс), `ForecastEntry` (`type='income'` для след. дохода, `type='expense'` для обязательных трат).
    *   **Реализуемость:** Да. Расчет на основе текущего баланса и будущих потоков до даты дохода.
    *   **Управление:** Пользователь определяет, какой доход считать "следующим крупным".

13. **Эффективность планирования**
    *   **Данные:** `Plan` (`status`, `target_amount`, `target_date`, `CurrentActualAllocatedAmount`), `CalculatedDiscrepancy`.
    *   **Реализуемость:** Да. "Индекс выполнения" – производная метрика (например, % планов в статусе `achieved`). Анализ причин – через `CalculatedDiscrepancy`.
    *   **Управление:** Пользователь анализирует.

14. **Нерегулярные доходы и расходы**
    *   **Данные:** `Transaction`, `Category`.
    *   **Реализуемость:** Да, если добавить флаг.
    *   **Предложение:** Добавить `Transaction.is_irregular: Boolean` или `Category.is_irregular: Boolean`.

15. **Календарь финансовых событий**
    *   **Данные:** `ForecastEntry` (`event_date`/`start_date`), `Transaction` (`transaction_date`), `Plan` (`target_date`).
    *   **Реализуемость:** Да. Отображаем события на календаре.
    *   **Управление:** Даты задаются при создании сущностей.

16. **Анализ нереалистичных планов**
    *   **Данные:** `Plan` (`CalculatedDiscrepancy`, `ProjectedBalance` для разных сценариев), история отклонений (см. Вьюху 11).
    *   **Реализуемость:** Да. Анализ систематических больших `CalculatedDiscrepancy` или большого разрыва между `optimistic` и `baseline`/`pessimistic` сценариями.
    *   **Управление:** Пользователь анализирует.

17. **Прогноз на год при текущем образе жизни**
    *   **Данные:** `Transaction` (для анализа прошлого), `ForecastEntry`, `DistributionRule`, `Scenario`.
    *   **Реализуемость:** Да. Требует логики для экстраполяции прошлых трат/доходов в будущие `ForecastEntry` для нового сценария "Текущий образ жизни".
    *   **Управление:** Пользователь инициирует создание такого прогноза.

18. **Прогноз на год с изменениями**
    *   **Данные:** `Scenario`, `ForecastEntry`, `DistributionRule`.
    *   **Реализуемость:** Да. Пользователь создает новый `Scenario` (возможно, на основе "Текущего образа жизни") и вносит изменения.
    *   **Управление:** Пользователь управляет сценариями.

**Итог:** Модель данных покрывает практически все вьюхи. Основные рекомендации: добавить флаг для транзитных планов и нерегулярных транзакций, и решить, как глубоко реализовывать историю прогнозов и анализ времени задержки средств, чтобы не нарушить простоту.
