Ниже я «до-доворачиваю» предыдущую модель, чтобы она:

гарантировала равенство «кошельки = транзакции = планы»;
давала управляемый over/under-flow, появлявшийся, когда «будущее стало прошлым»;
позволяла встраивать налоги, долги, активы с переоценкой, комиссионные кошельки и т. п.;
сохраняла понятность и минимум ручной работы.
────────────────────────────────────────
0. Напоминание ключевых сущностей
────────────────────────────────────────
Plan, Account, Transaction, TxLeg, MoneyStream, Scenario, InventorySnapshot.

Ни одной новой таблицы не добавляется; мы лишь уточним поля/статусы и алгоритм.

────────────────────────────────────────

План: уточнения к «паспорту» ────────────────────────────────────────
type расширяем до восьми значений
ACCUM | BUFFER | SINK | PASS | ASSET | LIABILITY | TAX_STASH | COMMISSION

status_periodic:  NONE | DAILY | WEEKLY | MONTHLY | YEARLY

rollover_policy:  KEEP | RESET | CAP (из прошлой версии)

linked_account_id nullable – для комиссионных кошельков (см. §7)

Балансные поля остаются теми же.

────────────────────────────────────────
2. «Будущее → прошлое»: четыре состояния ног
────────────────────────────────────────
TxLeg.state

PLANNED → DUE (дата наступила)
↙︎                 ↘︎
CLEARED             MISSED

• PLANNED: создан генератором, дата > today.
• DUE: дата ≤ today, но реальный перевод ещё не прошёл.
• CLEARED: унаследовал сумму факт-лега (см. reconciler ниже).
• MISSED: пользователь решил «платёж отменился».

Таким образом плановые суммы «не переписываются», а меняют state; исторический поток «как было задумано» остаётся виден.

────────────────────────────────────────
3. Reconciler (явная актуализация)
────────────────────────────────────────
Пользователь видит в «несовпадениях»:

• список DUE-ног (ожидали, но факта нет);
• список ACTUAL-легов без связанного PLANNED.

Доступны действия:

A) Match (закрыть): выбираем DUE и факт →
– DUE.amount = фактической сумме;
– state = CLEARED; фактический лег получает link_to_planned_id.
– Если ∆≠0 → создаётся Adjustment-Tx (см. ниже).

B) Skip (считаем, что плана не будет): state = MISSED, баланс плана не меняется.

C) Defer: сдвигаем planned_date → +N дней, state снова PLANNED.

Adjustment-Tx (over/under)
• auto-type = VARIANCE
• legs: +∆ к/из plan, –∆ на спец-план VARIANCE_POOL (type=BUFFER, priority=0).
VARIANCE_POOL всегда балансируется до нуля (см. §5), поэтому «откуда взялось/куда ушло» видно

────────────────────────────────────────
4. Инварианты «тройного равенства»
────────────────────────────────────────

Σ Account.balance_actual = A
Σ Plan.balance_actual = P
Σ InventorySnapshot.latest = I
Ограничения:

• Ledger гарантирует A = 0 (двойная запись).
• Voyeur-check раз в день:

a) ∆inv = I – (–A)     (кошельки ↔ леджер)
b) ∆plan = P – 0       (планы ↔ леджер)

Если |∆|>ε, UI показывает «расхождение», а деньги временно паркуются на:

• UNASSIGNED_ACCOUNT  (для кошельков)
• UNASSIGNED_PLAN     (для планов)

Пользователь решает, куда их «пришить».

────────────────────────────────────────
5. Родитель-дитя и «виртуальный собственный баланс»
────────────────────────────────────────
Вычисляемое правило:

balance_effective(parent) = own_legs(parent) + Σ children.balance_effective

где own_legs(parent) = Σ TxLegs, у которых plan_id = parent, child_id IS NULL.

Таким образом:

• Деньги НЕ хранятся дважды.
• Если пользователь раскидывает всё по детям – у родителя own_legs=0.
• Если хочет «поддерживать общий резерв» – кидает его в родителя.

Расхождение легко ловится: balance_effective(root) должно быть нулём.

────────────────────────────────────────
6. Дополнительные кейсы

6.1 Активы (квартира, акции)
• type = ASSET, rollover=KEEP, periodicity=NONE.
• valuation_formula = ‘areaprice_per_m²’ или ‘sharesclose_price(t)’.
nightly-job пишет TxLeg(+∆, plan=ASSET, -∆, plan=NET_WORTH_REVALUATION) – так переоценка попадает в леджер, но не путает кэш-флоу.

6.2 Долг
• type = LIABILITY (goal_amount < 0).
• деньги, отданные должнику: TxLeg(-cash_account, +LIABILITY) – долг «растёт».
• когда вернули – наоборот.

6.3 Налоговый счёт
• type = TAX_STASH, priority высокий, goal_date = дата уплаты.
• Engine-allocation льёт туда %.
• В день платежа Stream создаёт списание.

────────────────────────────────────────
7. Комиссионный кошелёк
────────────────────────────────────────
Иногда вывести 100 $ со счёта можно, но 2 $ съест комиссия.

• Account(id=BINANCE) – фактический баланс 100.
• Plan(linked_account_id=BINANCE, type=COMMISSION, valuation_formula='balance*0.02').
nightly-job разворачивает переоценку и кладёт её на COMISSION plan.
→ в интерфейсе видим «доступно к выводу 98».
Когда реально выводим, комиссия плюсуется к фактической транзакции, плана уже нет.

────────────────────────────────────────
8. Графики «план + факт»
────────────────────────────────────────
Для любой даты t:

• fact_series(t)   = balance_actual(t)
• plan_series(t)   = balance_planned(t) – balance_actual(now)   (что было задумано, ещё не случилось)
• variance_series  = fact_series – план_series (интеграл Adjustments)

На диаграмме видно, откуда взялся «нехватил/переизбыток».

────────────────────────────────────────
9. Что происходит со временем?
────────────────────────────────────────
Ночью (или при открытии приложения) cron:

Переводит PLANNED → DUE (dt≤today).
Выполняет rollover (RESET/CAP) по тем Plan, у которых начался новый период.
Дёргает valuation_formula для ASSET/LIAB/COMMISSION.
Запускает Engine-allocation для свободного кэша.
Пересчитывает materialized plan_balance_daily.
Пользователь всегда открывает «свеже-переваренное» состояние; все странности видны в списках DUE / ORPHAN-legs.

────────────────────────────────────────
10. Проверка на исходные требования

✓ over/under остаётся в истории – Adjustment-Tx.
✓ равенство сумм – UNASSIGNED-plan/account + nightly борьба за нуль.
✓ графики факт/план/variance – series из (balance_actual, balance_planned, adjustments).
✓ налоги, долги, комиссии, активы – via extra plan.type + valuation_formula.
✓ деньги не появляются/не пропадают – двойная запись + VARIANCE_POOL.
✓ просто пользоваться – обычно кликаем Match/Skip, остальное делает cron.

Если где-то останутся DUE-legs «висеть» неделями – это сознательный выбор пользователя, их видно красным, но модель не ломается. Всё реализуемо обычным Postgres + Python/TypeScript-бэкендом, без скрытой «магии».
