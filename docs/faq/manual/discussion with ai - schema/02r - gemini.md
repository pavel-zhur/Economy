Отлично, теперь картина стала гораздо яснее! Твои уточнения про слои, микро/макро планирование и, особенно, про простоту управления – это ключевые моменты.

Давай попробуем построить модель, учитывая эти цели. Ядро системы – это гибкое управление **виртуальными деньгами** в слое планирования, которое потом сверяется с реальностью.

## Предлагаемая модель данных (с акцентом на простоту и цели)

Мы сохраним идею трех слоев:
1.  **Слой Фактических Данных:** Кошельки и Транзакции.
2.  **Слой Планирования (Виртуальный):** Планы, Прогнозные События, Правила Распределения.
3.  **Слой Связей и Аналитики:** Как все это соединяется и анализируется.

---

### Сущности Слоя Фактических Данных 💳🧾

1.  **`User`** (Пользователь)
    * Как и раньше, стандартно.

2.  **`Account`** (Счет/Кошелек)
    * **Смысл:** Реальный источник денег (банк, наличные).
    * **Поля:** `id`, `user_id`, `name`, `type`, `currency_code`, `is_archived`.
    * **Важно:** Баланс этого счета *не хранится здесь напрямую*. Он определяется либо через `InventoryEntry`, либо как сумма транзакций (если нет инвентаризаций).

3.  **`InventoryEntry`** (Запись Инвентаризации)
    * **Смысл:** Снимок реального баланса `Account` на конкретную дату.
    * **Поля:** `id`, `account_id`, `entry_date`, `reported_balance`.
    * **Поведение:** Используется для сверки (Вьюха 5).

4.  **`Transaction`** (Фактическая Транзакция)
    * **Смысл:** Реальное движение денег.
    * **Поля:** `id`, `account_id`, `description`, `amount` (+/-), `currency_code`, `transaction_date`, `category_id` (опционально), `created_at_system`.
    * **Связь со слоем планирования:** Может быть (опционально) связана с `Plan` (через `TransactionPlanLink`, см. ниже), чтобы показать, какой план "покрыл" этот расход или в какой план "пошли" эти доходы.

5.  **`Category`** (Категория для транзакций)
    * Как и раньше, для общей классификации трат и доходов.

---

### Сущности Слоя Планирования (Виртуальный) 🧠📈

Это ядро твоей системы для управления будущим.

6.  **`Plan`** (План / Цель / Фонд / Конверт)
    * **Смысл:** Виртуальный контейнер для денег. Может быть целью накопления, бюджетом на категорию трат, запланированным крупным расходом.
    * **Поля:**
        * `id`, `user_id`, `name`.
        * `type` ('goal', 'fund', 'budget_category', 'planned_major_expense'). Тип 'budget_category' используется для регулярных, но неуточненных трат типа "карманные расходы".
        * `target_amount` (для 'goal', 'planned_major_expense').
        * `target_date` (для 'goal', 'planned_major_expense').
        * `parent_plan_id` (для иерархии).
        * `status` ('active', 'achieved', 'archived').
        * `priority` (число, для определения очередности пополнения через правила).
        * **`current_virtual_balance`**: *Это расчетное поле, показывающее, сколько денег сейчас числится на этом плане согласно всем прогнозам и распределениям на текущую дату. Не путать с фактическими деньгами.*
    * **Поведение:**
        * Его баланс во времени (будущий) – это то, что показывают графики.
        * Для простоты, `current_virtual_balance` – это скорее всего не хранимое поле, а вычисляемое на лету для конкретной даты (сегодня или в будущем) на основе `ForecastEntry` и `DistributionRule`.

7.  **`ForecastEntry`** (Прогнозная Запись / Поток)
    * **Смысл:** Это твой основной инструмент для описания *ожидаемых* денежных потоков – как доходов, так и расходов. Заменяет "Планируемые транзакции" и "регулярные планы трат".
        * Пример дохода: "Зарплата", "+50000", ежемесячно 1-го числа.
        * Пример расхода: "Аренда", "-20000", ежемесячно 5-го числа.
        * Пример "неуточненных трат": "Карманные расходы", "-5000", еженедельно по понедельникам. Этот расход будет *концептуально* уменьшать общий доступный пул денег или баланс связанного `Plan` типа `budget_category`.
    * **Поля:**
        * `id`, `user_id`, `description`.
        * `amount` (+ для дохода, - для расхода).
        * `currency_code`.
        * `start_date`.
        * `recurrence_rule` (например, RRULE, 'once', 'daily', 'weekly', 'monthly_on_day_X'). Позволяет описывать "continuous источники".
        * `end_date` (для повторяющихся).
        * `type` ('income', 'expense').
        * `linked_plan_id` (опционально):
            * Для дохода: не используется (доходы идут в общий котел, потом распределяются).
            * Для расхода: может указывать на `Plan`, из которого этот расход *предположительно* будет оплачен (например, `ForecastEntry` "Покупка телефона" связана с `Plan` "Фонд на новый телефон"). Это влияет на прогноз баланса конкретного плана.
        * `scenario_tag` (опционально, текстовая метка типа 'optimistic', 'pessimistic', 'baseline'. Позволяет иметь несколько слоев прогноза).
    * **Поведение:**
        * Это не деньги, а *ожидания*.
        * Именно эти записи формируют основу для прогнозов балансов планов и общего денежного потока.
        * При создании не нужно много полей. Основное: описание, сумма, как часто, с какой даты.

8.  **`DistributionRule`** (Правило Распределения / Трансфер)
    * **Смысл:** Описывает, как *виртуальные* деньги от `ForecastEntry` (доходы) или уже находящиеся в общем виртуальном пуле распределяются по `Plan`'ам. Также используется для трансферов между планами.
    * **Поля:**
        * `id`, `user_id`.
        * `source_description` (текстовое описание, например, "От Зарплаты" или "Ежемесячное пополнение").
        * `destination_plan_id` (в какой `Plan` идут деньги).
        * `amount_value` (конкретная сумма) ИЛИ `percentage_value` (процент от источника - *для продвинутой версии, можно начать с `amount_value`*).
        * `recurrence_rule` (как часто это правило применяется, например, "ежемесячно после зарплаты").
        * `effective_date_condition` (опционально, например, "начинать применять с 2025-08-01" или "когда баланс плана X > Y").
        * `priority` (для очередности выполнения правил, если денег на все не хватает).
        * `type` ('income_distribution_to_plan', 'plan_to_plan_transfer').
        * `source_plan_id` (только для `type = 'plan_to_plan_transfer'`).
        * `scenario_tag` (опционально, для привязки правила к сценарию).
    * **Поведение:**
        * **Простота управления:** Пользователь создает правило типа: "Каждый месяц, 5-го числа, переводить 10000 в план 'Отпуск'". Или "После каждого поступления 'Зарплата', 10% в план 'Инвестиции'".
        * Для микро-менеджмента: "Сегодня, перевести 500 из 'Общие средства' в 'План на продукты'". Это `DistributionRule` с `type='plan_to_plan_transfer'`, `recurrence_rule='once'`, `effective_date_condition='today'`.
        * Не требует мгновенного указания даты для всех перераспределений на "континууме". Правило сработает согласно своей `recurrence_rule` и `effective_date_condition`.
        * Эти правила применяются движком прогнозирования для расчета будущих балансов планов.

9.  **`Scenario`** (Сценарий Прогноза)
    * **Смысл:** Именованный набор предположений для прогнозирования (например, "Базовый", "Оптимистичный с премией", "Пессимистичный без подработки").
    * **Поля:** `id`, `user_id`, `name`, `description`.
    * **Поведение:** `ForecastEntry` и `DistributionRule` могут быть помечены `scenario_tag`. При расчете прогноза для конкретного `Scenario` учитываются записи с соответствующим тегом или без тега (общие для всех).

---

### Сущности Связей и Вспомогательные

10. **`TransactionPlanLink`** (Связь Транзакции с Планом)
    * **Смысл:** Опционально связывает фактическую `Transaction` с одним или несколькими `Plan`. Это нужно для анализа "план/факт" и для коррекции баланса плана по факту траты/поступления.
    * **Поля:** `id`, `transaction_id`, `plan_id`, `amount_linked` (какая часть транзакции относится к этому плану).
    * **Поведение:**
        * **Простота линковки:** Может создаваться полуавтоматически (система предлагает варианты на основе описания/суммы) или вручную. Можно одну транзакцию разбить на несколько планов.
        * Не обязательна для каждой транзакции. Важна для ключевых трат или для отслеживания бюджета по категориям-планам.
        * Когда создается такая связь, это может корректировать *представление* о деньгах на плане, но фактические деньги уже учтены в `Transaction`.

---

## Как это работает вместе (особенно слой планирования):

1.  **Основа прогноза – `ForecastEntry`:** Пользователь заводит ожидаемые доходы ("Зарплата", "Доп. доход") и расходы ("Аренда", "Средние траты на еду"). Это формирует общий прогноз денежного потока.
2.  **Распределение по планам – `DistributionRule`:** Пользователь создает правила, как деньги из общего потока (или с одного плана на другой) распределяются по его `Plan`'ам (целям, фондам). Например, "10% от 'Зарплаты' в 'Отпуск'", "5000 ежемесячно в 'Фонд ЧП'".
3.  **Расчет балансов планов во времени (для графиков и анализа):**
    * Система берет все `ForecastEntry` и `DistributionRule` (учитывая `scenario_tag`, если выбран сценарий).
    * Начиная с некоторой точки (например, сегодня или начало года), она симулирует движение денег по дням/неделям/месяцам:
        * Применяет `ForecastEntry` (доходы увеличивают "общий виртуальный пул", расходы уменьшают его или баланс связанного `Plan`).
        * Применяет `DistributionRule` (деньги перетекают из "общего пула" или между планами в целевые `Plan`'ы).
    * Результат – временной ряд прогнозируемых балансов для каждого `Plan` и общего пула. Это и есть данные для Вьюх 3, 8, 9, 10, 12, 16, 17, 18.

**Простота и гибкость:**

* **Создание планов:** Просто имя и тип. Цели/даты опционально.
* **Планирование потоков:** Через `ForecastEntry`. Не нужно создавать миллион отдельных будущих транзакций. Описал поток "100$ в неделю на карманные расходы" – система сама его учтет.
* **Распределение:** `DistributionRule` описывают намерения. Можно настроить один раз и забыть (для регулярных) или создавать разовые для микро-менеджмента.
* **Микро-уровень:** Создание разового `DistributionRule` ("перекинуть X из плана А в план Б сегодня") или корректировка баланса плана через `TransactionPlanLink` после фактической траты.
* **Макро-уровень:** Анализ графиков, созданных на основе долгосрочных `ForecastEntry` и `DistributionRule`. Изменение приоритетов в `DistributionRule` или сумм в `ForecastEntry` сразу покажет новую картину будущего.
* **"Не важно когда именно перераспределения":** `DistributionRule` с гибкими `recurrence_rule` и `effective_date_condition` решают это. Если дата не указана явно, правило сработает по своему расписанию. Для графиков система будет использовать это расписание.

**Связь слоев и "равенство богатства":**

1.  **`Сумма InventoryEntry.reported_balance` (по последним записям для каждого Account) == Фактическое богатство.**
2.  **`Начальный баланс системы + Сумма всех Transaction.amount` == Фактическое богатство, объясненное потоками.**
    * Эти два должны сходиться (Вьюха 5). Расхождение – ошибка учета или реальная потеря/находка.

3.  **Связь с планированием (самое тонкое):**
    * **Фактические деньги на планах:** Сумма `TransactionPlanLink.amount_linked` (приходные) для конкретного `Plan` минус сумма `TransactionPlanLink.amount_linked` (расходные). Это то, сколько *реальных* денег было ассоциировано с этим планом.
    * **"Третье равенство" (сумма планов = богатство):** Это равенство выполняется для *виртуального слоя на текущий момент*. Общий прогнозируемый баланс всех планов + нераспределенный остаток на текущую дату должен сходиться с текущим фактическим богатством, если модель полна.
    * Т.е., `Фактическое богатство` = `Сумма(Plan.current_virtual_balance на сегодня для базового сценария) + Нераспределенный_виртуальный_остаток_на_сегодня`.
    * Это позволяет ответить: "У меня есть X денег. По моим планам, они распределены вот так..."

**Линковка транзакций (простота):**

* Система может предлагать `Plan` для линковки на основе названия `Plan`, его `type`, описания `Transaction` и суммы.
* Для "карманных расходов": одна `Transaction` на большую сумму (например, снятие наличных) может быть частично прилинкована к `Plan` "Карманные расходы на неделю". Или мелкие транзакции по карте автоматически линкуются к соответствующим планам-бюджетам по правилам пользователя (например, все транзакции в "Starbucks" -> план "Кофе").

Эта модель пытается минимизировать количество сущностей и сделать их поведение более гибким за счет `type` и правил. `ForecastEntry` и `DistributionRule` – это два мощных инструмента для слоя планирования. Сложность переносится в движок прогнозирования, а для пользователя взаимодействие с системой должно быть проще.
