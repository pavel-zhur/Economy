Ниже ‒ два минималистичных, но «эластичных» варианта модели, которые перекрывают все описанные вьюхи.  
Обе модели строятся вокруг одной идеи: «деньги лежат в ведрах, а любое событие – это перемещение денег между этими ведрами».  
Разница лишь в том, как именно оформлены «ведра».

────────────────────────────────────────
Вариант A. Единое «Ведро» (Bucket = счёт, фонд, расходный план …)
────────────────────────────────────────

1. Bucket  
   • id, user_id  
   • kind (enum: EXTERNAL_WALLET, FUND, SAVING, EXPENSE_PLAN, INCOME_PLAN)  
   • parent_id (иерархия «план-подплан»)  
   • auto_spend (bool) – «съедает всё, что пришло»  
   • goal_amount, goal_date, pessimistic_floor, …  
   • archived_at  

   Поведение:  
   – баланс = Σ всех проводок по bucket_id;  
   – FUND и SAVING могут иметь goal_*;  
   – EXPENSE_PLAN может уходить в минус;  
   – INCOME_PLAN используется только как источник распределений.

2. Transaction  
   • id, dt, status (PLANNED | ACTUAL), comment, scenario_id(null)  
   – не хранит сумму! Сумма сидит в линиях.

3. TxLeg  
   • tx_id → Transaction  
   • bucket_id → Bucket  
   • amount_signed (дебет +, кредит –)  

   Любое движение денег – это запись N строк вида (+10000 на ZARPLATA_INCOME, –10000 со счёта TINKOFF_RUB).

4. ScheduleTemplate  
   • id, bucket_id, cron / rrule, default_legs(JSON)  
   – даёт повторяющиеся PLANNED-транзакции.

5. AllocationRule  
   • id, from_bucket_id (обычно INCOME_PLAN или «Не-распределено»)  
   • to_bucket_id, percentage / fixed_amount, priority, effective_from…  
   – позволяет строить прогноз «как распределятся будущие доходы».

6. InventorySnapshot  
   • id, bucket_id (только EXTERNAL_WALLET)  
   • dt, factual_balance  

7. Category  
   • id, title  
   – вешается на Transaction либо на TxLeg (если нужно разрезать один платёж по категориям).

8. Scenario  
   • id, name, baseline_dt_from, baseline_dt_to  
   – хранит набор гипотетических Transaction/AllocationRule, не мешая «живым» данным (вьюха 10, 18).

9. Derived / материализуемые штуки  
   – bucket_balance_daily (bucket_id, date, balance) – удобнее строить графики 3, 8, 14.  
   – income_usage (income_tx_id, leg_id, days_to_use) – источник для вьюхи 6.

Ключевые связи:
• Bucket 1 — N TxLeg  
• Transaction 1 — N TxLeg  
• Bucket 1 — N ScheduleTemplate / AllocationRule / InventorySnapshot / Goal (goal столбцы можно вынести в отдельную таблицу, если нужно версионировать цели)

Почему этого хватает

• «Баланс планов во времени» – линия bucket_balance_daily.  
• «Отрицательные планы и неподкреплённые транзакции» – запрос, где bucket.kind ≠ EXTERNAL и баланс<0, плюс Transaction, в котором все леги указывают только на EXTERNAL buckets.  
• «Распределение фактических денег по планам» – доля Σ(balance) группой kind.  
• «Планируемые расходы» – bucket.kind = EXPENSE_PLAN ∧ dt_planned ≤ today ∧ balance>0 …  
• Инвентаризация – сравниваем Σ TxLeg по EXTERNAL bucket с последним InventorySnapshot.  
• Forecast / What-If – берём baseline + обогащаем Scenario-проводками.

Плюсы:  
+ Всего одна сущность «деньги-контейнер» → простая агрегация, нет специальных джойнов «план-категория».  
+ True double-entry: всегда пара ног – легко ловить расхождения.  
+ «Физические» и «виртуальные» деньги живут в одной системе координат → автоматические проверки консистентности.  
Минусы:  
– «Ведро» перегружено смыслом (кошелёк, фонд, план…). На UI нужно четко фильтровать виды.  
– category via Leg усложняет аналитику, если операция разбита на 10 ведёр.

────────────────────────────────────────
Вариант B. Явное разделение «Счёта» и «Плана»
────────────────────────────────────────

1. Account (EXTERNAL only)  
   • id, title, currency

2. Plan  
   • id, type (FUND, SAVING, EXPENSE, INCOME)  
   • parent_plan_id, auto_spend, goal_*, pessimistic_floor

3. Transaction  
   • id, dt, status (PLANNED/ACTUAL), account_id (откуда/куда деньги физически ушли), comment

4. PlanAllocation  
   • id, tx_id, plan_id, amount_signed  
   – связывает Т-ки и планы (многие-ко-многим). Нога в «двойной записи» хранится в самой Transaction (со счётом), а детализация «на какой план» ‒ здесь.  
   – если строки нет → «неподкреплённая транзакция».

5. RecurringTemplate  
6. AllocationRule (как в варианте A, но from_account или from_plan=INCOME)  
7. Goal  
8. InventorySnapshot  
9. Category

Плюсы:  
+ Логически чище: «кошелёк» и «план» – разные сущности.  
+ План может быть в минусе, а счёт – нет (нативное ограничение).  
Минусы:  
– Все запросы, где нужны одновременно balances счётов и balances планов, чуть более громоздкие (две таблицы).  
– Для «дельта-движка» придётся писать триггер: изменение PlanAllocation должно менять виртуальный баланс плана.

────────────────────────────────────────
Что из «тонкого» учтено

1. Деньги «под план, но ещё не истрачены» – это положительный баланс фонда/расходного плана.  
2. «Авто-съедающие» планы (auto_spend) исключаются из прогнозов и круговых диаграмм простой WHERE-фильтром.  
3. Нерегулярные поступления/платежи – просто непериодические Transaction; их можно выбрать COUNT(*) < N в интервале.  
4. Цели, pessimistic_floor, точечные goal markers – всё живёт в Bucket / Goal.  
5. What-If не пачкает основную ленту: scenario_id в Transaction позволяет строить параллельный поток.  
6. Задержка средств – days_between(income_leg.dt, first(expense_leg.dt)).  

────────────────────────────────────────
Как выбрать между А и B

• Если нравится «один общий леджер, дальше тегируем» – берите А: проще писать отчёты; легче строить агрегаты «Все деньги = 0».  
• Если важен жёсткий контроль, чтобы «virtual» и «physical» активы не путались – берите B: модель ближе к домашней бухгалтерии «счёт ↔ план».  

Любая из моделей остаётся компактной (≈ 10 таблиц) и без дополнительных сущностей закрывает все заявленные вьюхи.
